# Loop 稼働集計（`/loop-uptime`）実装計画

設計書: `docs/superpowers/specs/2026-08-14-uptime-design.md`

## Global Constraints

1. **完全に読み取り専用**（集計側）。`STATE.md` / `events.jsonl` / GitHub を書き換えない。
   テストで「実行後にファイルの mtime が変わらない」ことを確かめる
2. **観測のための記録がループ本体を止めない。** `record_event` は既に失敗を握りつぶす
   設計になっている。EXIT トラップも同じ原則で、失敗しても firing の終了コードを変えない
3. node 標準ライブラリのみ。python3 は使わない（決定 6）
4. 層構造: 純関数（`uptime.mjs`）/ I/O（`uptime-cli.mjs`）/ bash（`bin/loop-uptime`）
5. 既存テストを壊さない（着手時点 349 件）

## 設計書からの細部の詰め

### `finish` が持つ `outcome` は「生の kind」にする

設計書 §5.2 は `dispatched` / `skipped` / `failed` / `idle` / `unknown` という
語彙を導入していたが、**実装では `finish.outcome` にその tick で最後に書かれた
判断イベントの kind をそのまま入れる**（判断イベントが無ければ `none`）。

理由: 語彙を 2 つ持つと、`KINDS` が増えたときに両方を更新する必要があり、片方の
更新漏れが「黙って別のバケツに落ちる」形になる。kind → 表の列の対応は集計側
（`uptime.mjs`）の 1 か所に閉じ込め、そこを `KINDS` と機械照合する。

### 最後の kind は `record_event` に覚えさせる

firing の 11 か所を再び触って `FIRING_OUTCOME=...` を書き足すのは、配線漏れを
作るだけ。`record_event` 自身に覚えさせる（1 か所）。

`while ... done < <(...)` の本体は現在のシェルで走る（bash のプロセス置換）ので、
fix / automerge ループの中で呼ばれても変数は残る。

## Task 1: イベントに `start` / `finish` を足す

### `.loop/lib/events.mjs`

```js
export const KINDS = [
  'start',            // tick の開始。gh を叩く前に書く
  'finish',           // tick の終了。EXIT トラップで書く
  'conflict',
  ...
];

export const NUMERIC_FIELDS = [
  'issue', 'pr', 'round', 'open_prs', 'max_prs', 'today', 'max_today',
  'duration_ms',      // finish の所要時間
  'rc',               // firing の終了コード
];
```

### `.loop/lib/events-cli.mjs`

`--field start_ms=<epoch ms>` を受けたら、**`start_ms` は出力せず** `duration_ms` に
変換する。時刻の差を node 側で取るのは、`date +%s%3N` が GNU 拡張で BSD date
（macOS。bats はホストで走る）に無いため（P3 の `stamp()` と同じ理由）。

```js
// start_ms は入力専用。経過時間に変換して捨てる
if (fields.start_ms !== undefined) {
  const started = Number(fields.start_ms);
  delete fields.start_ms;
  if (Number.isFinite(started)) fields.duration_ms = Math.max(0, Date.now() - started);
}
```

### テスト（`events.bats` に追加）

- `start_ms` を渡すと `duration_ms` になり、`start_ms` 自体は出力に残らない
- 不正な `start_ms` では `duration_ms` を付けない（壊れた行を作らない）
- `KINDS` と firing の配線の双方向照合（既存テスト）が `start` / `finish` を含めて通る

## Task 2: `firing` に開始・終了を記録する

### `.loop/lib/common.sh`

```bash
# 直近に記録した kind。EXIT トラップが「この tick の結末」として使う。
# 各呼び出し箇所に書き足すと 11 か所の配線漏れを作るので、ここで一括して覚える
LOOP_LAST_KIND=""

record_event() {
  local kind="$1"; shift
  ...
  LOOP_LAST_KIND="$kind"
}

# tick の開始時刻（epoch ms）。date +%s%3N は BSD date に無いので node で取る
now_ms() { node -e 'process.stdout.write(String(Date.now()))'; }
```

### `.loop/bin/firing`

先頭（`cd "$REPO_ROOT"` の直後、git fetch より前）:

```bash
# --- tick の開始を記録する ------------------------------------------------
# gh を叩く前に書く。ネットワーク待ちで固まった tick を「始まったが
# 終わっていない」として検出できるようにするため（設計書 決定 2）
if [ "$DRY" = 0 ]; then
  FIRING_START_MS="$(now_ms)"
  record_event start
  LOOP_LAST_KIND=""   # start 自体は「結末」ではない

  # 終了経路は 11 か所ある。個別に書くと必ず漏れ、漏れた経路がそのまま
  # 「記録されない失敗」になる。EXIT トラップ 1 か所で全部を拾う。
  # rc は必ずハンドラの先頭で捕まえる（後続のコマンドが上書きするため）
  firing_finish() {
    local rc=$?
    record_event finish \
      "start_ms=$FIRING_START_MS" \
      "rc=$rc" \
      "outcome=${LOOP_LAST_KIND:-none}"
    return "$rc"
  }
  trap firing_finish EXIT
fi
```

**`--dry-run` では設置しない。** 既存の `record_state` / `record_event` と同じ扱いで、
DRY は履歴を汚さない。

**トラップは firing の終了コードを変えない。** `return "$rc"` で元の値を保つ。
観測のための記録がループ本体の判定を書き換えてはいけない。

### テスト（`firing.bats` に追加）

- 通常の tick で `start` と `finish` が 1 行ずつ出る
- `finish` に `duration_ms` と `rc` と `outcome` が入る
- `idle` の tick の `outcome` が `idle` になる
- `--dry-run` では `start` も `finish` も出ない
- **firing が非 0 で終わる経路（conflict）でも `finish` が出る**
- トラップが firing の終了コードを変えない

## Task 3: 集計の純関数（`.loop/lib/uptime.mjs`）

I/O を持たない。以下を export する。

| 関数 | 役割 |
|---|---|
| `charWidth(cp)` / `width(s)` | 東アジア全角を 2 桁として数える |
| `pad(s, w, align)` | 幅を揃える |
| `table(headers, rows, aligns)` | 罫線つきの表を作る。行ごとに区切り線を入れる |
| `OUTCOME_BUCKETS` | kind → 表の列の対応（§5.2）。`KINDS` と照合する |
| `foldTicks(events)` | events を tick 単位に畳む（start/finish/判断 を 1 レコードに） |
| `aggregateByDay(ticks)` / `aggregateByWeek(ticks)` | 日別・週別のサマリ |
| `breakdown(ticks)` | 種別ごとの 回数 / 合計 / 平均 / 割合 |
| `overThreshold(ticks, ms)` | 閾値超の一覧 |
| `missingSlots(ticks, hours, from, to)` | 期待スロットと `start` の実績の差 |
| `formatDuration(ms)` | `8h46m` / `14m53s` 形式 |
| `MEASURING_FROM` の扱い | `duration_ms` を持つ finish が 1 件も無い先頭の連続日を `(計測前)` にまとめる |

### 全角判定

node に `east_asian_width` 相当は無いのでコードポイント範囲で判定する。

```js
// 幅 2 とみなす範囲。参照実装は unicodedata.east_asian_width の W/F を使うが、
// node には無いため主要な範囲で近似する。日本語の見出しと罫線が揃えばよい
const WIDE = [
  [0x1100, 0x115f], [0x2e80, 0xa4cf], [0xac00, 0xd7a3],
  [0xf900, 0xfaff], [0xfe30, 0xfe6f], [0xff00, 0xff60], [0xffe0, 0xffe6],
];
```

### `(計測前)` の扱い

`duration_ms` を持つ tick が 1 件も無い**先頭の連続日**を 1 行にまとめ、稼働時間欄に
`(計測前)` と出す。**`0m00s` と表示してはいけない**（0 分と「記録が無い」の混同。
mmm-loops が実際に踏んだ）。

## Task 4: CLI と起動スクリプト

### `.loop/lib/uptime-cli.mjs`

```
用法: loop-uptime [--month YYYY-MM | --all] [--weekly] [--threshold 30m] [--plain]
```

- `loops/events.jsonl` を読む（`events.mjs` の `parseLines` を再利用）
- 発火スロットは `.loop/bin/gen-crontab` の出力から取る（`control-plane.mjs` の
  `parseCrontabHours` を再利用。crontab を自前で解釈しない）
- `--plain` はタブ区切り。罫線を描かない（他ツール連携用）
- **書き込みは一切しない**

### `.loop/bin/loop-uptime`

```bash
#!/usr/bin/env bash
# Loop の稼働集計。読み取り専用。
set -uo pipefail
source "$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)/../lib/common.sh"
exec node "$LIB_DIR/uptime-cli.mjs" "$@"
```

## 実装順序

Task 1 → 2 を先に済ませる。**データが溜まり始めないと、表を作っても中身が無い。**
2 時間ごとに 1 tick なので、Task 3 以降を作っている間に少しずつ溜まる。

## 検証手順

1. 全 bats が緑（既存 349 件 + 新規）
2. dev-loop で fixture を食わせて 3 つの表を目視（罫線のズレを確認）
3. akashic-recorder に展開し、実データで `loop-uptime --all` を叩く
4. 次の firing を待ち、`start` / `finish` が対で記録されることを確認
5. **数日〜1 か月ぶん溜めてから、mmm-loops と同じ病気（総稼働時間の 62% が
   ハング）がないかを見る。** これが本来の目的であり、表を作ることではない
