# Loop 稼働集計（`/loop-uptime`）設計書

出所: mmm-loops（`~/code_box/org/tam/mmm-services/mmm-loops`）からの申し送り。
参照実装 `scripts/loop-uptime.sh`（221 行、bash + python3 埋め込み）。

前提: P3（コントロールプレーン）実装済み。`loops/events.jsonl` が存在する。

## 1. 目的

ループが**いつ・何回・どれだけの時間**動いていたかを 1 コマンドで表にする。

mmm-loops で 8 月の 46 発火・26 時間 05 分を集計したところ、**総稼働時間の 62% が
「失敗するまでに 2 時間以上ハングしていた時間」**だった。1 発火 1〜2 分で終わるのは
正常時だけで、異常時は数時間止まってから落ちるのが常態化していた。この事実は
STATE.md を人間が目で追っても分からず、集計して初めて見えた。

**この機能の価値は表そのものではなく、「タイムアウトを入れるべきだ」という判断材料が
出てくること。** dev-loop でも、まず溜めて同じ病気がないかを見る。

## 2. 着手前に確認した前提（申し送りの指示による）

| 確認項目 | 結果 |
|---|---|
| 所要時間が記録されているか | **記録されていない。** `firing` に `trap` / `SECONDS` / `date +%s` が一切ない |
| 1 tick のイベント構造 | 1 行のみ。しかも `dispatch` は Maker 起動の**前**に書かれ、終了時刻を含まない |
| 発火ごとのコスト | **記録されていない。** `budget-check` は完全に読み取り専用 |
| 置き場所 | **申し送りの前提が逆。** dev-loop がテンプレート本体（`origin` = `loop-engineering-dev-template`）。`.loop/**` が template 所有なのは**ここが配布元だから**であり、ここに置かないと派生プロジェクトに配られない |
| 既存データ量 | akashic-recorder に 12 行（22 時間ぶん）。P3 で入れたばかり |

**したがって本作業の大半は「集計の実装」ではなく「集計できるデータを作ること」になる。**

## 3. 達成条件

1. 日別の 発火数 / skip / 失敗 / dispatch / 稼働時間 を表で出せる
2. 種別ごとの内訳（回数・合計・平均・割合）を出せる
3. 閾値（既定 30 分）を超えた発火の一覧を出せる
4. **発火するはずだったのに記録が無いスロット**を出せる（§5.3）
5. 日本語見出しで罫線がズレない（全角 2 桁計算）
6. 計測データが無い期間は `0m00s` ではなく **`(計測前)`** と明示する
7. 完全に読み取り専用。`STATE.md` / `events.jsonl` / GitHub を一切書き換えない
8. `.loop/**` に置き、派生プロジェクトに配られる

## 4. 決定事項

| # | 決定 | 理由 |
|---|---|---|
| 1 | **1 tick に `start` と `finish` の 2 行を足す。** 既存の判断イベント（`dispatch` 等）はそのまま残す | 判断イベントは途中で書かれるため終了時刻を持てない。終了時にだけ書く設計にすると、SIGKILL された tick が丸ごと消える——**それが一番知りたいデータ**なのに |
| 2 | `start` は firing の**最初**に書く（gh を叩く前） | ネットワーク待ちで固まった tick を「始まったが終わっていない」として検出するため。後ろに置くと、その区間のハングが見えない |
| 3 | `finish` は **EXIT トラップ**で書く。全終了経路（正常・gate 失敗・予算 skip・途中 exit）を 1 か所でカバーする | 終了経路は現在 11 か所ある。個別に書くと必ず漏れ、漏れた経路がそのまま「記録されない失敗」になる |
| 4 | `--dry-run` では `start`/`finish` とも書かない | 既存の `record_state` / `record_event` と同じ扱い。DRY は履歴を汚さない |
| 5 | **コスト列は作らない** | 発火ごとの消費を記録していない。列を埋めるには `firing` が毎回 ccusage を 2 回叩くことになり、観測のために本体を重くする。`budget-check` を読み取り専用に保つ判断（P1）も崩したくない |
| 6 | 実装は **node**（bash ラッパー + `.mjs`）。python3 は使わない | コンテナに python3 はあるが、このリポジトリは `config.mjs` / `gate.mjs` / `events.mjs` と一貫して node を埋め込んでいる。参照実装が python3 なのは mmm-loops の流儀 |
| 7 | 判定・整形は純関数（`uptime.mjs`）、I/O は CLI（`uptime-cli.mjs`）、起動は bash | 既存の層構造に合わせる |
| 8 | kind → 表の列の対応表を**テストで機械照合**する | 値域（`KINDS`）が増えたときに分類が漏れると、増えた分が黙って「その他」に落ちる。P3 で同じ形の照合を 3 か所に入れている |

### 4.1 なぜ `start` / `finish` を別 kind にするか

既存イベントに `duration_ms` を足す案も検討したが、採らない。判断イベントは
「何を決めたか」を書いた時点で確定させたい（それ自体が価値のある記録）。
所要時間は別の関心事で、混ぜると「書く時点」の制約が衝突する。

## 5. イベントの追加

`KINDS` に 2 つ足す。

```json
{"ts":"2026-08-14T13:00:00+09:00","kind":"start"}
{"ts":"2026-08-14T13:00:03+09:00","kind":"finish","duration_ms":3120,"outcome":"idle","rc":0}
```

| フィールド | 意味 |
|---|---|
| `duration_ms` | `start` からの経過ミリ秒 |
| `outcome` | その tick の結末（§5.2） |
| `rc` | firing の終了コード |

### 5.1 所要時間の測り方

bash の `SECONDS` は秒精度で、正常時の 1〜2 秒を区別できない。`date +%s%3N` は
GNU 拡張で BSD date（macOS。bats はホストで走る）にない。**`events.mjs` の
タイムスタンプ生成と同じく node 側で処理する**（P3 の決定と同型）。

`record_event finish` を呼ぶ際に `start_ms` を渡し、CLI 側で現在時刻との差を取る。

### 5.2 `outcome` の値域と表の列の対応

`finish` の `outcome` は、その tick で最後に書かれた判断イベントの kind から決める。
判断イベントが 1 つも無い tick（gh 呼び出しで落ちた等）は `unknown`。

| 表の列 | outcome | 対応する既存 kind |
|---|---|---|
| dispatch | `dispatched` | `dispatch`, `fix` |
| skip | `skipped` | `skip` |
| 失敗 | `failed` | `gate_failed`, `automerge_failed`, `fix_exhausted`, `conflict` |
| （空振り） | `idle` | `idle`, `report`, `gate_retry`, `automerge` |
| （不明） | `unknown` | 判断イベント無し |

**この表の網羅性をテストで照合する**（`KINDS` の全要素がいずれかに現れること）。

### 5.3 未発火スロットの検出

mmm-loops の事故（5 時間半ハングした発火が次の枠を丸ごと潰し、気づくのが遅れた）は
dev-loop では **firing 側では記録できない**。supercronic が
`not starting: job is still running` を出して firing を起動しないため、firing の中の
どんな記録も走らない。

代わりに**外側から検出する**。`gen-crontab` が発火時刻（例: `1,3,5,...`）を持っているので、
期待されるスロットと `start` イベントの実績を突き合わせ、`start` が無いスロットを
「未発火」として一覧に出す。これは events.jsonl だけを読むので読み取り専用のまま。

## 6. 出力

3 つ（＋条件付きで 1 つ）の表を出す。参照実装と同じ切り口。

1. **日別サマリ** — 日付 / 発火 / skip / 失敗 / dispatch / 稼働時間
2. **稼働時間の内訳** — 種別ごとの 回数 / 合計 / 平均 / 割合
3. **閾値超の発火** — 日付 / 時刻 / 所要 / 結果
4. **未発火スロット** — 1 件以上あるときだけ

`firings_per_day = 12`（mmm-loops は 6）で日別だと行が増えるため、`--weekly` を用意する。

```
用法: loop-uptime [--month YYYY-MM | --all] [--weekly] [--threshold 30m] [--plain]
  --plain  タブ区切り。他ツール連携用（罫線を描かない）
```

### 6.1 罫線と全角

node に `east_asian_width` 相当は無いので、コードポイント範囲で判定する
（`U+1100-115F`, `U+2E80-A4CF`, `U+AC00-D7A3`, `U+F900-FAFF`, `U+FE30-FE6F`,
`U+FF00-FF60`, `U+FFE0-FFE6` を幅 2）。参照実装と同じく `width()` / `pad()` /
`table()` の 3 関数に閉じ込め、**この 3 つを純関数としてテストする**。

行ごとに区切り線を入れる（値を縦に読みやすくするため。参照実装の判断を踏襲）。

### 6.2 `(計測前)` の扱い

`duration_ms` を持つ `finish` が 1 件も無い先頭の連続日は 1 行にまとめ、稼働時間欄に
`(計測前)` と出す。**`0m00s` と表示してはいけない**（0 分と「記録が無い」の混同。
mmm-loops が実際に踏んだ）。

## 7. ファイル構成

```
新規 [T]

  .loop/lib/uptime.mjs           純関数: 集計・幅計算・表の描画
  .loop/lib/uptime-cli.mjs       I/O: events.jsonl と gen-crontab を読む
  .loop/tests/uptime.bats

変更 [T]
  .loop/lib/events.mjs           KINDS に start / finish、数値フィールドに duration_ms
  .loop/lib/events-cli.mjs       finish の経過時間計算
  .loop/lib/common.sh            record_event_start / record_event_finish
  .loop/bin/firing               先頭で start、EXIT トラップで finish
  .claude/skills/loop-status/    「詳しい稼働集計は /loop-uptime」への導線
```

`.loop/**` は template 所有なので、派生プロジェクトに配られる。

## 8. テスト戦略

P1〜P3 と同じ 3 層。

1. **純関数**: 幅計算（全角・半角・混在）、`(計測前)` の判定、集計、閾値抽出、未発火スロットの算出
2. **CLI**: fixture の `events.jsonl` を食わせて表が出ること。読み取り専用であること（実行後にファイルの mtime が変わらない）
3. **散文と実装の照合**:
   - `KINDS` の全要素が §5.2 の対応表のいずれかに現れる
   - `firing` の全終了経路が `finish` を書く（EXIT トラップ 1 か所なので、トラップの設置を照合）
   - `--dry-run` で `start`/`finish` が書かれない

## 10. スコープ外

| 項目 | 理由 |
|---|---|
| コスト列 | 決定 5。発火ごとの消費を記録していない |
| タイムアウトの導入 | **この集計の結果を見てから決める。** 先に入れると、何分で切るべきかの根拠が無い |
| ロック衝突の firing 側での記録 | 構造上できない（supercronic が firing を起動しない）。§5.3 の外側からの検出で代替する |
| コントロールプレーンへの表示 | まず CLI で形を固める。UI に出すかは実データを見てから |
