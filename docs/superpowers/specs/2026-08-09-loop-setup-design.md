# P2 — ワンショットセットアップ（`/loop-setup` + `/loop-doctor`）設計書

作成日: 2026-08-09
前提: P1（ハーネス核）実装済み。`docs/superpowers/specs/2026-08-05-dev-loop-harness-design.md`

---

## 1. 目的

クローンから常駐開始までを 1 コマンドに畳む。加えて、**設定の不整合が品質を静かに殺すのを構造的に防ぐ**。

2 つ目は当初の P2 定義になかったが、P1 の最終レビューで見つかった 4 件の merge ブロッカーのうち 2 件が「実装のバグ」ではなく「セットアップの不備」だったため、達成条件に加える。

| P1 で見つかった不備 | 症状 |
|---|---|
| `[project] test/lint` を設定して `extra_tools` が空 | Verifier がテストを 1 つも実行せず、diff だけ読んで approve する |
| GitHub ラベル 3 つが未作成 | ラベル操作はすべて best-effort なので、待ち行列もエスカレーションもエラーを出さずに機能しない |

どちらも現在は README に手順を書くことで塞いでいる。**README は飛ばせる。**

---

## 2. 達成条件

- [ ] **A.** クローン後、1 コマンドでループが常駐状態になる（人間の手作業は認証 2 つのみ）
- [ ] **B.** `[project]` の test / lint / preview をリポジトリから自動検出して提案する
- [ ] **C.** 設定の不整合をセットアップ時点で検出する（実行時まで持ち越さない）
- [ ] **D.** 必須の外部状態（GitHub ラベル 3 つ）をセットアップが作る
- [ ] **E.** セットアップ完了を検証し、何が有効で何が未設定かを一覧で報告する
- [ ] **F.** 再実行が安全（冪等）。途中で失敗しても、もう一度叩けば続きから進む
- [ ] **G.** `maturity` の初期値を `L1` にする
- [ ] **H.** 設定の崩れをセットアップ後もいつでも検出できる

## 3. 決定事項

| # | 決定 | 理由 |
|---|---|---|
| 1 | `/loop-setup` は**ホストの `claude` セッション**で走る | コンテナ内で走らせると、セットアップが用意するはずの「コンテナ内 `claude` の認証」を前提にしてしまい循環する。テンプレートをクローンした人は手元で Claude Code を使っている前提が置ける |
| 2 | 成果物は **`/loop-setup` と `/loop-doctor` の 2 本** | setup は一度しか走らないが、設定の崩れ（config 編集・ラベル削除・認証期限切れ）はいつでも起こる。検証を独立させる |
| 3 | 検査ロジックは **`.loop/bin/loop-doctor`**（シェルスクリプト）に置く | スキルは散文でテストできない。P1 の F1 と `/loop-status` の集計ズレは、どちらも「散文とコードの実態がズレる」種類のバグで、213 件のテストが 1 つも捕まえられなかった。ヘルスチェック自体が散文だと同じ穴に落ちる |
| 4 | `config.toml` は**上書きせず差分を当てる** | seeded（同期で触られない）扱いのファイル。再実行でユーザーの編集を壊してはいけない |
| 5 | `Dockerfile` は**自動編集しない**。提案 → 承認 → マーカー付きブロックに追記 | 他人のビルド定義を黙って書き換えるのは踏み込みすぎ |
| 6 | `maturity` の初期値は **`L1`** | 数回観察してから昇格する、という README の思想と揃える |
| 7 | **Docker を使わない経路は P2 のスコープ外** | 対応すると常駐の仕組みを OS ごとに書くことになり、P2 が別物になる |
| 8 | **`firing` からは `loop-doctor` を呼ばない** | 12 回/日の実行に検査コストを足すと「空回りゼロ」が壊れる。呼ぶのは `/loop-mtg` と手動のときだけ |

## 4. `/loop-setup` の流れ

```
① 前提チェック
   docker / gh / git の有無を確認。無ければ入れ方を示して中断する

② プロジェクト検出
   package.json の scripts / Makefile / pyproject.toml / Cargo.toml 等から
   test / lint / preview を推測し、人間に確認を取る
   検出できなければ聞く

③ config.toml の生成
   [project] と [agents.claude] extra_tools を必ずセットで書く
   既存の値は尊重し、差分だけ当てる
   maturity は L1

④ Dockerfile の提案
   検出した言語のツールチェーン行を提示し、承認を得てマーカー付きブロックに追記

⑤ ラベル 3 つの作成
   ホストの gh で作成。ホストに gh が無ければコンテナ経由に切り替える

⑥ ビルドと起動
   docker compose -f docker/compose.yml up -d --build

⑦ 認証 2 つ（人間の手作業）
   コマンドを提示してユーザーに叩いてもらい、完了を待つ
     docker compose -f docker/compose.yml exec loop claude
     docker compose -f docker/compose.yml exec loop gh auth login

⑧ /loop-doctor の実行
   全項目の合否を一覧で表示して終わる
```

⑦以外はスキルが進める。**「ターミナルを開くのは 1 回だけ」がここで完成する。**

### 冪等性

各ステップは「既に済んでいるか」を先に判定し、済んでいれば飛ばす。
途中で失敗しても、もう一度 `/loop-setup` を叩けば続きから進む。

---

## 5. `/loop-doctor` の検査項目

`.loop/bin/loop-doctor` が検査を行い、スキルは結果を人間向けに整えるだけの薄い層にする。

| 検査 | 落ちたときに何が起きるか |
|---|---|
| GitHub ラベル 3 つの存在 | 待ち行列（`loop:ready`）もエスカレーション（`needs-human`）も、エラーを出さずに機能しない |
| `[project] test/lint` と `extra_tools` の対応 | Verifier がテストを実行せず diff だけでレビューする |
| `claude` / `gh` の認証 | 期限切れが静かに起きる |
| `config.toml` の構文 | 壊れると `gen-crontab` が「1 回/日」に丸め込み、コンテナは Up のまま発火回数だけ減る |
| cron の実際の発火時刻 | 設定と実際のズレ |
| 残骸の worktree | 誰も所有していない `-verify-pr-*` は、その PR の検証を永久に止める |
| コンテナの稼働 | `Up` だが中身が壊れている状態 |

### インターフェース

```
loop-doctor            # 全検査。合否を 1 行ずつ出力
loop-doctor --quiet    # 失敗した項目だけ出力
```

終了コード: 0 = 全項目合格 / 1 = 1 件以上の失敗。

### 呼ばれる場所

- `/loop-setup` の最後（⑧）
- `/loop-mtg` の①（毎朝の会議で自動的に健全性が確認される）
- 人間が手動で

## 6. ファイル構成

```
.claude/skills/
  loop-setup/SKILL.md      [T] 新規。ホストで走る対話セットアップ
  loop-doctor/SKILL.md     [T] 新規。loop-doctor を呼んで結果を整える
.loop/bin/
  loop-doctor              [T] 新規。検査の実体
.loop/lib/
  detect-project.mjs       [T] 新規。test/lint/preview の自動検出（純関数 + CLI）
.claude/skills/loop-mtg/SKILL.md  [T] 変更。①に loop-doctor の実行を足す
README.md                         [T] 変更。手順を /loop-setup に置き換える
```

`.loop/OWNERSHIP.toml` の分類は既存のルールで自動的に template 扱いになる（`.loop/**` と `.claude/skills/**`）。新しいルールは不要。

## 7. テスト戦略

P1 と同じく 3 層。

1. **`detect-project.mjs` のユニットテスト** — 各種プロジェクト形式の fixture から正しくコマンドを検出するか。純関数にして I/O を分離する
2. **`loop-doctor` の bats テスト** — 各検査項目の合格・不合格ケース。`gh` はスタブ、`docker` もスタブ
3. **スキルの検証** — フロントマターの検査と、スキルが参照するコマンド・パス・config キーが実在することの照合

**3 は P1 で最も高くついた種類の検証なので、機械的に行う。** `/loop-status` の集計ズレは、スキルの散文が実装とズレた結果だった。

## 8. 受け入れ基準

- [ ] 空のプロジェクトで `/loop-setup` を実行すると、認証 2 つを除いて常駐状態に到達する
- [ ] `package.json` を持つプロジェクトで test / lint が自動検出され、確認を経て `config.toml` に書かれる
- [ ] `[project] test` を設定して `extra_tools` を空にすると、セットアップが**その場で**警告して先に進まない
- [ ] `/loop-setup` を 2 回実行しても、1 回目の設定が壊れない
- [ ] `config.toml` に手で加えた変更が、再実行後も残っている
- [ ] `loop-doctor` がラベル欠落・認証切れ・config 構文エラー・残骸 worktree をそれぞれ検出する
- [ ] `loop-doctor` の終了コードが 0/1 で正しく分岐する
- [ ] `/loop-mtg` の①で `loop-doctor` が実行される
- [ ] `Dockerfile` は承認なしに書き換わらない
- [ ] `maturity` の初期値が `L1` になっている
- [ ] 既存の 213 件のテストが引き続き緑

## 9. スコープ外

| | 理由 |
|---|---|
| Docker を使わないホスト常駐 | OS ごとの常駐登録が必要になり、P2 が別物になる |
| `docker.sock` を渡すかの選択 | 現状は compose のコメントで削除箇所を明示済み。対話に載せるのは P3 以降 |
| 既存リポジトリへの後付け導入 | dev-loop は同居型。設計前提の変更にあたる |
| セットアップ結果の GUI 表示 | P3 |
