# DECISIONS（設計判断の追記専用ログ）

決着した議論を蒸し返さないための記録。形式: 日付 / 決定 / 理由。

## 成熟度ラダーについて

| | 動作 |
|---|---|
| L1 | firing は判定と報告だけ。dispatch しない |
| L2 | Maker → PR → Verifier まで自動。**merge は人間**（既定） |
| L3 | Verifier approve かつ `loop:auto-merge` ラベルがあれば自動 merge |

**L1 から始める。** 信頼は実績で獲得する。最初から L3 を与えない。
L3 のラベル限定は「低リスクの雑務のみ自動 merge する」を機械的に効かせるためのもの。
自動 merge は「あ、これ違った」の検出を事後にし、巻き戻しコストを上げる。

## 2026-08-10: 適用範囲を個人リポジトリ専用と定める

**決定:** dev-loop は個人が単独で所有するリポジトリ専用とする。
チーム共有リポジトリでの利用は想定しない。複数の既存リポジトリを
`src/` 等に置いてまとめて回す用途は、別テンプレートとして分離する。

**理由:** ループの状態は GitHub の共有領域に置かれている。
Issue が待ち行列、PR が判定単位、ラベルが状態機械であり、いずれも
リポジトリ全体で共有される。チームリポジトリに入れると、個人の実験が
そのまま全員に見える（ラベルの追加、1 日最大 12 件の PR、Issue への
コメント、100 ファイル超の増加、L3 での自動マージ）。技術的には
動作するが、同意なく持ち込める変更ではない。

**この制約の出どころ:** 2026-08-05 の設計会議で真実の源を選ぶ際、
「GitHub Issues + PR」を採用し、「リポ内の markdown ファイル（git が履歴）」を
退けた。前者は PR が Verifier の判定単位として最初から存在するため実装量が
激減する一方、共有インフラへの依存を買っている。本決定はその代償を
明示的に受け入れるもの。ローカル完結型が必要になった場合は、
退けた案が出発点になる。

**範囲内:** 個人が所有する既存プロジェクトへの導入（ハーネス一式を
コピーする。手順は README を参照）。

## 2026-08-14: README.md を template 所有から seeded に移す

**決定:** `README.md` の所有区分を `[T] template`（同期で常に上書き）から
`[S] seeded`（テンプレートが初期版だけ置き、以後触らない）に変更する。

**理由:** README は派生プロジェクト自身の説明になる文書であり、テンプレート
所有のままだと、プロジェクトの README を書いた瞬間に次の同期がテンプレートの
説明文で上書きして消す。`CLAUDE.md` は同じ理由で最初から seeded になっており、
README だけが template に入っていたのは分類の誤り。

**見つかった経緯:** 最初の派生プロジェクト（akashic-recorder）の README が、
導入から 4 日経っても「# dev-loop 開発用 Loop Engineering テンプレート」の
ままだった。P3 の同期漏れを点検していて気づいた。実害が出る前に見つかったが、
プロジェクトの README を書いてから同期していれば、その内容は消えていた。

**境界変更のリスクについて:** 2026-08-05 の設計で「所有境界は P1 で確定させる。
境界を後から引き直すと既存の派生プロジェクトが壊れる」と決めたが、今回の変更は
**上書きする対象を減らす方向**なので、既存の派生プロジェクトを壊さない。逆向き
（seeded → template）の変更は同じ理屈が使えないため、引き続き慎重に扱う。

**あわせて入れた検査:** README の「導入済みのプロジェクトでハーネスを更新する」
手順が seeded なパスをコピーしていないことを、`.loop/tests/skill-references.bats`
で `OWNERSHIP.toml` と突き合わせる。散文の手順と境界定義がズレるのを防ぐ。
